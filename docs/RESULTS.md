## 1. Viability bars: refined before judging

The brief's provisional bars were: >90% direction on material changes, >90% recall on large (>50%)
regressions, a low false-positive rate, useful magnitude buckets, and a cheap, fast check. The lab
exposed three problems with them.

1. **"Material" must sit above the measurement noise floor.**
   - Single-run CV is 5–29% for 0.2–10 s statements (E-009). The noise model fitted on repeated
     MAIN runs gives a log-SD of 0.045 for statements over 1 s and 0.07–0.14 below 1 s.
   - Seven of 26 scenarios (s02, s03, s08, s09, s12, s15, s24) have a truth whose class changes
     across the four truth repetitions: their true impact sits near ±10%.
   - We keep **10%** as the threshold. We report both the full set and the stable-truth subset.
2. **"Material" has two denominators:**
   - relative to the affected workloads (the PR comment's "+Y%"), and
   - relative to the whole production bill (economic materiality).

   A 4.5× regression in a model that is a small part of a busy affected set is only +5% of that set
   (s08). We score both views: ≥10% of the affected workloads, and ≥1% of the total bill.
3. **"Cheap and fast" needs a denominator.** We express CI cost as k, the number of production-run
   equivalents per analysis (**measured**), and as the break-even run frequency against the risk
   the check removes (E10).

Refined bars used in `DECISION.md`:

| Bar | Threshold |
|---|---|
| Direction accuracy, material changes | ≥ 90% |
| Large-regression recall (≥ +50%, incl. new workloads) | ≥ 90%, and ≥ 75% flagged at ≥ +50% ("strict") |
| False warnings on immaterial changes | ≤ 20% |
| Magnitude within one bucket (±10/25/50/100%) | ≥ 80% |
| CI cost | k ≤ ~2, and break-even frequency ≤ the workload's actual run frequency |
| CI latency | ≈ production runtime of the affected models + ~1 min of dbt overhead |

## 2. E1: can the per-run impact be estimated before merge? (`MEASURED (local engine)`)

- **Benchmark:** 26 PRs against a 17-model dbt project on TPC-H SF2.
  - **Truth:** the median of 4 production-scale repetitions per variant.
  - **Estimators** use only CI-available information: a single full-clone run, production history
    of MAIN from separate repetitions, sample environments, and `EXPLAIN`.
- **Mix:** 16 material changes (11 increases, 1 new model, 4 decreases), 10 immaterial, and 9 large

  - s18's CI estimate was −7% against a truth of +81%;

- **Stable-truth subset** (19 scenarios; the 7 near-threshold ones removed): the full-clone A/B

### 2.3 Mechanisms behind the failures of cheap strategies (per-workload evidence)

1. **Scale-dependent direction.**
   - s22 (add ORDER BY): the model is 38% *cheaper* at production scale, where the full clone
     measures −19% and the truth is −27%. In the 10% and 1% samples it is a regression (+22%,
     +41%). The sign of the cost change flips with data size.
   - s14 (join pre-aggregation, −29%): 1% Bernoulli, last-90-days and two-point estimates all say
     +21% to +40%.
2. **Super-linear joins** (s06, truth +1,413%). The 1% key-consistent sample says +4%, the 10% says
   +570%, two-point extrapolation says +4,264%, and the static C_out says +124,924%. One full-clone
   run says +1,419%.
3. **Compute-bound changes are invisible to static and byte signals.** s17 (windows/ranks/medians,
   +56% per run) registers 0% on both bytes and plan cardinality; s22 registers 0% on bytes and +6%
   on cardinality.
4. **Bytes ≠ compute.**
   - s02 (pruning defeated): bytes +239%, time +4%.
   - s04 (incremental→full): bytes +856%, time +62%.
   - s13 (fewer columns): bytes −35%, time −40%, so the two can also agree.

   Separately, the latency ratio and the CPU-work ratio of the *same* model differ by up to ~3×,
   because parallel efficiency differs between variants and with data size (E-028).
5. **Data-dependent no-ops.** s15's removed filter matched no rows in the window (truth ≈0; E-029).
   A code-reading estimator predicts +33% rows.
6. **Scale-limited truth for incremental windows.** s03 and s24 (3→45-day lookback) are small at SF2
   (+7%, +0%). E8 shows the cause is fixed per-statement overhead on tiny increments, not pruning
   granularity. At production volume, a 15× larger reprocessing window would be a large regression
   of the hourly job, so lab truth understates these cases.
7. **Time-window CI data cannot see window changes.** s01 (window 180→730 days): the last-90-days
   sample says −5%, while the truth is +111%.
8. **PR-only-vs-history is fragile for tiny, high-frequency workloads** (s04). A 7 ms dashboard
   query's history median (10.9 ms) vs one CI run (7.3 ms), × 30,000 runs/month, swamped a +673%
   per-run regression of the hourly model. A paired A/B cancels drift like this; comparing against
   history does not.

## 3. E9: change detection and attribution (H1) (`MEASURED`, dbt-core 1.12.5)

`results/tables/attribution.md` compares three detectors on 26 PRs: changed files, dbt
`state:modified` and a rendered-SQL diff.

- **25/26:** dbt's `state:modified` matched the rendered-SQL diff exactly at model level.
  - Macro fan-out (s23) was caught via the `macros` sub-selector (3 models).
  - Folder-level config inheritance (s25) was caught via `configs` (5 staging models).
  - In-file materialisation changes (s04, s10, s11) were caught via `body` + `configs`.
- **1 miss, s24:** a var default changed in `dbt_project.yml`. dbt reported nothing, while the
  hourly incremental model now reprocesses 15× more days (E-023). The rendered-SQL diff catches it.
  With union detection the model is measured at +28% per run at lab scale. E8 shows this lab figure
  is limited by fixed overhead, not by layout.
- **Changed ≠ costlier.**
  - s21 (a cosmetic refactor with a CTE rename) is flagged by both detectors. Whitespace/comment
    normalisation does not canonicalise identifiers. Its truth is −1%.
  - s23 (a macro edit touching 3 models plus descendants) has a truth of +1%.
  - Detection selects *where to look*; only measurement says whether it matters. The hybrid's static
    screen resolved 58 of 108 workload-analyses without execution. Most were unchanged downstream
    workloads with identical plans.
- **Consumers are outside dbt.** Mapping changed relations to BI queries used the lab's registry, the
  stand-in for `ACCESS_HISTORY` / `JOBS.referenced_tables` / `table_lineage`. §2.4 shows this is not
  optional.

## 4. E5: can confidence be grounded quantitatively? (computed from `MEASURED` noise)

Intervals come from Monte Carlo propagation of *measured* noise only:
- a single CI run's log-SD by duration band, fitted on repeated MAIN runs (0.045 above 1 s,
  0.07–0.14 below 1 s);
- the history anchor's noise (3 reps);
- for the hybrid's sample path, the disagreement between the 1% and 10% ratios.

Labels follow from the interval:
- **HIGH:** the whole 80% interval lies in one class (increase / immaterial / decrease).
- **MEDIUM:** it spans two classes.
- **LOW:** it spans both material directions.

| estimator | 80% interval coverage of truth | direction accuracy by label |
|---|---|---|
| Full-clone A/B × history | **84%** (21/25) | HIGH 100% (n=19) · MEDIUM 67% (n=6) · LOW – (n=0) |
| Hybrid | 80% (20/25) | HIGH 94% (n=16) · MEDIUM 71% (n=7) · LOW 100% (n=2) |

The new model s16 is excluded because its relative impact is infinite. Per-scenario intervals are in
`results/tables/uncertainty.md`.

- **Coverage is close to nominal, and the grade is informative:** HIGH was never wrong on direction
  for the full-clone estimator. So *in the lab*, uncertainty can be represented honestly with
  intervals built from repeated-run noise.
- **The four misses are instructive:**
  - s12 and s19: the truth sits near a boundary, or is dominated by millisecond consumers.
  - s14 and s22: the direction was right but the interval was too narrow. There is systematic
    CI-vs-truth drift of 7–9 points that run-to-run noise does not capture.
- **This interval covers only measurement noise.** A production interval must also include the
  following, none of which the lab could quantify on a real platform:
  - CI-vs-production condition gaps: warehouse size, concurrency, cache (E3);
  - physical layout (no effect in E8, but untested on real micro-partitions);
  - frequency uncertainty (E6);
  - the pool-policy range (E2).

## 5. E7: does post-merge calibration improve estimates? (computed from `MEASURED` pairs)

Leave-one-scenario-out multiplicative correction on (predicted, realised) per-workload pairs, using
material, same-sign pairs only:

| estimator | pairs | median abs log error: before | global factor (LOO) | per-class factor (LOO) | learned factor |
|---|---|---|---|---|---|
| Full-clone A/B × history | 38 | 0.16 | **0.14** | 0.19 | 1.08 |
| Hybrid | 31 | 0.16 | 0.15 | 0.18 | 1.08 |
| 10% key-consistent sample | 34 | 0.42 | 0.55 | 0.57 | 1.28 |
| Two-point extrapolation | 32 | 0.70 | 0.84 | 0.64 | 0.88 |
| Bytes | 28 | 0.62 | 0.52 | 0.55 | 1.13 |
| Static C_out | 22 | 1.32 | 1.10 | 1.13 | 0.46 |

- **Accurate estimator:** its small systematic bias (reads ~8% low) is learnable, and a global
  factor helps a little.
- **Sample-based estimators:** calibration makes them *worse*. Their errors are scenario-specific
  (scale-dependent plan and parallelism effects), not a stable bias. Calibration cannot turn a
  cheap, wrong-sign estimator into a reliable one.
- **Per-class factors overfit at this sample size.**
- **No evidence either way on cross-customer transferable signal.** All pairs come from one engine
  and one synthetic customer (see `ARCHITECTURE.md` §6).

## 6. E8: does physical layout change the truth? (`MEASURED (local engine)`)

Identical data was rewritten with 8,192-row row groups (~1.7 days of line items each), against the
default of 122,880 rows (~26 days at SF2):

| scenario | PR/MAIN ratio, default row groups | PR/MAIN ratio, fine row groups |
|---|---|---|
| s01 widen window | 2.50 | 2.39 |
| s02 cast defeats pruning | 0.99 | 1.01 |
| s03 incremental lookback 3 → 45 days | 1.21 | 1.17 |
| s04 incremental → full table | 5.88 | 5.78 |
| s13 fewer columns | 0.58 | 0.60 |

**The hypothesis is rejected:** layout granularity did not change any ratio materially here.

- **Why incremental-window changes look small at SF2:** fixed per-statement overhead, not pruning
  granularity. s03 and s24 reprocess ~214k extra rows, which is milliseconds of work against
  ~18 ms of fixed cost per run. At 100× data, the same change would multiply the hourly job's
  scan work ~15×.
- **Consequence:** the lab *underestimates* incremental-window regressions. Scale-limited truth is
  itself a finding: a CI run on smaller-than-production data would make the same mistake.
- **s24 was not re-measured here** because the layout script uses dbt-state detection, under which
  s24 has an empty plan. s03 covers the same mechanism.

## 7. E10: is the checker economical? (Phase 11) (`MEASURED` k, `ASSUMED` rates)

A check that executes k production-run equivalents, `pushes` times per PR, pays for itself only if

`k × pushes ≤ P(material regression) × E[relative regression] × runs_per_month × months_undetected`.

Here k is measured per strategy (E1, median over the 26 PRs). The break-even run frequency is swept
over P ∈ {5%, 20%}, E[r] ∈ {+50%, +100%}, months ∈ {1, 3} and pushes ∈ {1, 3}:

| strategy | k (median, MEASURED) | break-even runs/month: min / median / max |
|---|---|---|
| Full-clone A/B | 4.6 | 7.7 / **69** / 552 |
| PR-only vs history | 2.5 | 4.1 / **37** / 299 |
| 10% key-consistent sample | 1.6 | 2.7 / **24** / 196 |
| Hybrid | 4.0 | 6.7 / **60** / 480 |
| Static plan | 0 | 0 |

Interpretation:
- The only strategy that met the accuracy bars (the full clone) pays for itself, at median
  assumptions, only on workloads that run **more than ~70 times a month**. That means hourly jobs,
  frequently rebuilt models, and dashboard queries. A PR-only run against history (~2.5 runs)
  roughly halves that, to more than daily.
- A **monthly** job (s17) can never justify a clone run: one CI analysis costs ~4.6 of its monthly
  runs. The largest per-run regressions in infrequent heavy jobs are therefore uneconomic to catch
  pre-merge by execution.
- **The hybrid does not reduce CI cost** (k 4.0 vs 4.6). The static screen saved execution on
  unchanged downstream workloads (58 of 108 workload-analyses). But the sample stage was then
  spent on the changed workloads, and most of them escalated to a full clone anyway. Samples are
  an extra cost, not a substitute.
- The **max** k (≈30–36) comes from super-linear regressions (s06) and large blast radii (s25). The
  check is most expensive exactly when the PR is most dangerous. A per-PR spend cap with a
  "too expensive to measure → block and ask" outcome is a product requirement.
- On Snowflake every CI resume also bills a 60 s minimum (E-011). Short CI statements therefore
  cost more than their runtime suggests, which penalises sample-based CI further (`INFERRED`).

## 8. E2: from usage deltas to recurring dollars (`SIMULATED` month under `DOCUMENTED` billing rules)

Each scenario's measured usage (truth medians) is replayed through a 30-day production month.
The month includes all other workloads at their measured baseline, the job schedules and BI traffic
of `production_context.yaml`, and seven pool configurations. Full tables:
`results/tables/economics_summary.md`. Units: lab seconds and bytes × κ=100 (`ASSUMED`). Cells
below are **marginal $/month** (bill with PR − bill with MAIN) / **naive attributed $/month**
(Δ usage × unit price, i.e. what per-query attribution would report):

| scenario | Snowflake dedicated | BigQuery on-demand | BigQuery editions | Databricks SQL serverless |
|---|---|---|---|---|
| s01 widen window (batch) | +90 / +90 | +10 / +10 | +62 / +34 | +126 / +126 |
| s04 incremental → full (hourly) | +47 / +49 | +282 / +282 | +38 / +25 | +66 / +69 |
| s06 super-linear join (batch) | +208 / +208 | +1 / +1 | +109 / +93 | +292 / +292 |
| s10 table → view (BI consumers) | **−11 / +57** | +166 / +166 | −9 / +14 | −15 / +79 |
| s11 view → table (BI consumers) | **0 / −25** | −67 / −67 | 0 / −13 | 0 / −35 |
| s18 frequent cheap view (BI) | **0 / +12** | +1 / +1 | 0 / 0 | 0 / +17 |
| s25 staging layer → tables | +317 / +328 | +44 / +44 | +86 / +42 | +368 / +459 |

Findings:
1. **Batch jobs on dedicated warehouses: attributed ≈ marginal** (ratio ≈1.0). The documented
   60 s minimum and idle tail are second-order for multi-minute jobs. Here "cost per run ×
   frequency" is a fair estimate.
2. **Consumer workloads on a busy BI warehouse: marginal ≈ 0**, and the sign can flip (s10: −$11
   marginal vs +$57 attributed). The synthetic BI warehouse is up for all business hours, so extra
   query seconds are absorbed until concurrency forces a second cluster. This is **HD confirmed as a
   mechanism**: the number depends on whether you price short-run marginal spend (≈0) or capacity
   consumption (attributed). That is a **policy choice**, not a measurement.
3. **The same change differs by orders of magnitude across billing models.**
   - Compute-heavy s06: +$208 on Snowflake vs +$1 under BigQuery on-demand.
   - Byte-heavy s04 (full rebuild): +$282 on-demand vs +$47 on Snowflake.

   The ranking of PRs by cost impact is therefore platform-dependent. A cross-platform "cost impact"
   number is meaningful only with the pool's billing model attached (H6).
4. **Capacity pricing adds rounding effects.** BigQuery editions' 50-slot steps and 60 s holds made
   the marginal cost of transform-pool batch changes exceed attributed slot-seconds (s01: $62 vs
   $34). The BI pool's 100 baseline slots absorbed consumer changes entirely.
5. **Sensitivity to κ** (time/data scale 10 → 1000, Snowflake dedicated) preserves every pattern
   above:
   - consumer-driven changes stay absorbed (s19: $0 vs +$167 attributed at κ=1000);
   - batch changes stay ≈ attributed.

   Idle-tail effects grow for the short hourly job (s03 at κ=1000: +$8 marginal vs +$45 attributed).

**Caveat.** These numbers show *mechanisms under documented rules applied to a synthetic month*. They
are not forecasts. The replay model itself has **not** been validated against real metering
(`WAREHOUSE_METERING_HISTORY` / `RESERVATIONS_TIMELINE` / `system.billing.usage`). Doing so is the
first item of the live experiment. One defect in the simulator was found and fixed during this work:
float residue created phantom autoscale charges (E-032).

## 9. E3: does a CI measurement transfer to production *conditions*? (`MEASURED (local engine)`)

E1's full clone ran under the same conditions as its truth, which flatters it. E3 re-measures six
scenarios under conditions where CI and production typically differ. Each cell is the PR/MAIN
total-latency ratio; the percentage is its deviation from the production reference (4 threads,
isolated, warm, 3 interleaved reps):

| scenario | production reference | CI on smaller engine (1 thread) | production under concurrent load | cold single run (no warm-up) |
|---|---|---|---|---|
| s01 widen window | 2.36 | 3.00 (+27%) | 1.95 (−18%) | 2.14 (−10%) |
| s04 incremental → full | 6.78 | 15.98 (+136%) | 10.70 (+58%) | 4.79 (−29%) |
| s05 many-to-many join | 1.67 | 1.94 (+16%) | 1.58 (−5%) | 1.63 (−3%) |
| s08 window functions | 2.26 | 3.44 (+52%) | 2.52 (+12%) | 2.00 (−11%) |
| s09 repeated scans | 1.26 | 1.28 (+1%) | 1.28 (+1%) | 1.26 (−0%) |
| s22 add ORDER BY | **0.81** | **1.10 (+35%, sign flip)** | 0.90 (+11%) | 0.78 (−4%) |

The background load is two concurrent heavy aggregations on the same engine, like tenants of one
warehouse. It slowed absolute runtimes 2.6–4.5×.

- **Warehouse size must match production.**
  - A smaller CI engine overstated regressions by up to 136%, because MAIN and PR parallelise
    differently.
  - It flipped the sign of s22: an improvement in production, a regression on the small engine.
  - `INFERRED` for Snowflake: an X-Small CI warehouse is not a valid proxy for a Large production
    warehouse. CI must run on the production size, or be calibrated per pool. s22 shows the error
    is not a constant factor.
- **Concurrency shifts ratios by −18% to +58% while preserving direction here.** It is irreducible
  pre-merge (it depends on what else runs), so it belongs in the uncertainty interval, not in the
  point estimate.
- **Protocol matters.** A cold, unwarmed single run understated ratios by up to 29%. Warm-up plus
  interleaving (E1's protocol) is required.
- **Implication for accuracy:** E1's 100% direction for the full clone is an *upper bound*. Under
  realistic condition gaps, a HIGH-grade verdict needs same-size CI compute and a
  concurrency-widened interval. See `DECISION.md` Q3.

| s25 | 32.2 | 78.2 | 83.1 | 83.2 |
| s23 (macro fan-out) | 30.3 | 34.1 | 34.1 | 34.1 |

- **One hop is enough within the dbt DAG here.** Executing direct children captured nearly all of the
  DAG-downstream effect (s01: +87% → +98%; s26: +20% → +25%). Deeper descendants added execution
  cost without accuracy. In s25 they cost 2.6× the direct run for a 1-point change.
  - `INFERRED` caveat: this project's DAG is shallow (≤3 levels). Deeper DAGs with fan-out would make
    "all descendants" more expensive, not more informative. It is not shown that 1 hop always
    suffices.
- **Consumers dominate "downstream" economics.** The largest downstream effects came from non-dbt
  consumers (s10, s11, s18, s19). A DAG-only strategy gets them wrong or misses them entirely.
- **Row-count elasticity is cheap but unreliable.** It scales descendants by the modified model's
  output-row ratio, without executing them.
  - It was accurate for s26 (+30% vs +33%).
  - It overstated s01 by 82 points: one descendant filters to recent months, so its cost did not
    scale with rows.
  - It is usable as a screen ("rows changed ⇒ execute that descendant"), not as an estimate.
- **Verdict on the Phase 9 options:** downstream propagation is "useful one or a few hops
  downstream", plus consumers. Exhaustive descendant execution is CI-expensive for little gain.
  Static propagation is too noisy to trust for magnitude.

## 11. E6: frequency extrapolation (SIMULATED)

Recurring cost = per-run Δ × future runs, and runs must be forecast from telemetry. For each
pattern, 300 synthetic 180-day histories were generated and the next 30 days forecast
(`experiments/frequency.py`; `results/tables/frequency.md`):

| pattern (SIMULATED) | median rel. error, trailing 30 d | p90 | median rel. error, trailing 90 d | Poisson 80% coverage | empirical-range coverage |
|---|---|---|---|---|---|
| cron_daily | 0.000 | 0.000 | 0.000 | 1.00 | 1.00 |
| cron_hourly_with_retries | 0.004 | 0.010 | 0.003 | 1.00 | 0.76 |
| monthly_job | 0.000 | 0.000 | 0.000 | 1.00 | 1.00 |
| bi_weekday | 0.073 | 0.082 | 0.061 | 0.00 | 0.00 |
| bi_growing_5pct_month | 0.023 | 0.030 | 0.037 | 0.00 | 1.00 |
| seasonal_peak_in_forecast | 0.666 | 0.671 | 0.667 | 0.00 | 0.00 |
| adhoc_sparse | 1.000 | 2.000 | 0.667 | 0.72 | 0.83 |
| data_arrival_driven | 0.103 | 0.263 | 0.086 | 1.00 | 0.73 |

- **Cron schedules:** exact to within 1%.
- **Weekday-patterned BI traffic:** 6–8% error from calendar composition alone. Naive Poisson
  intervals *never* covered the truth: calendar and trend structure, not count noise, drive the
  error.
- **Seasonal peaks absent from history:** missed by ~67% (a 3× peak). Not predictable from history.
- **Sparse ad-hoc jobs:** ±100%.
- **Data-arrival-driven rebuilds** (dbt-State-style skipping): ~10% median error, 26% at p90.
