Experiment results · 28 September 2026

Cost CI lab results

Twenty-six adversarial dbt pull requests, eleven ways to estimate their cost impact before merge, and nine follow-up experiments. Only a paired run of both versions on production-scale data got every material change right. Every cheaper method got at least one wrong.

The decision drawn from these results is on the Cost CI Verdict page.

Section 1

Viability bars, refined before judging

The brief proposed: more than 90% correct direction on material changes, more than 90% recall on large regressions, few false positives, useful magnitude buckets, and a cheap, fast check. The lab showed three problems with those bars as written.

  • Materiality has to sit above measurement noise. A single run varies by 5–29% for statements of 0.2–10 seconds. Seven of the 26 scenarios had a true impact near ±10%, so their class changed between repetitions. The threshold stays at 10%, and results are reported with and without those seven.
  • Materiality needs two denominators. A change is judged relative to the workloads it touches (the "+Y%" a PR comment shows) and relative to the whole production bill. A 4.5× regression in one model came to only +5% of its busy affected set (s08).
  • "Cheap and fast" needs a unit. CI cost is measured as k, the number of production runs one analysis consumes, and turned into a break-even run frequency.

Robustness checks

  • Stable truth only. With the seven near-threshold scenarios removed (19 remain), the full clone scores 100% direction, 100% recall, no false warnings and 95% within one bucket. The ranking of strategies does not change.
  • CPU work instead of elapsed time. The ordering holds. Samples do better on work than on elapsed time (the 10% sample reaches 95% direction) because work scales more linearly than parallel run time. The full clone still has no sign errors.
  • Share of the whole bill. Counting a change as material when it moves the total production bill by 1% or more, the full clone scores 84% direction and the PR-only run 95%. Most of these changes are driven by millisecond dashboard queries, where a single CI measurement stays noisy even at five executions.

Why the cheap strategies fail

  • The sign can flip with data size

    Adding an ORDER BY (s22) made the model 38% cheaper at production scale, while the 10% and 1% samples showed it as a regression of +22% and +41%. For a join optimisation (s14, truth −29%), three cheap estimators reported increases of +21% to +40%.

  • Super-linear joins break extrapolation

    Self-joining line items on ship date and ship mode (s06) made the affected workloads about 15 times as expensive (+1,413%). The 1% key-consistent sample showed +4%, the 10% sample +570%, two-point extrapolation +4,264%, and the static plan +124,924%. One full-clone run measured +1,419%.

  • Compute-bound changes are invisible to plans and bytes

    Adding windows, ranks and medians (s17, +56% per run) moved neither bytes nor plan row estimates. Adding an ORDER BY (s22) left bytes unchanged and moved row estimates only 6%.

  • Bytes and compute diverge

    Comparing dates as strings, which defeats pruning (s02), raised bytes scanned 239% but engine time only 4%. Replacing an incremental model with a full rebuild (s04) raised bytes 856% and time 62%. They can also agree: dropping two text columns (s13) cut bytes 35% and time 40%. Separately, the latency ratio and the CPU-work ratio of the same model differed by up to 3×, because parallel efficiency differs between variants and with data size.

  • Some changes are no-ops on the actual data

    Removing the filter that excluded returned items (s15) reads in code as +33% rows. On this data the filter excluded no rows in the model's window, so the true change was about zero. Only execution shows this.

  • Small increments hide incremental-window changes

    Reprocessing 45 days instead of 3 (s03, s24) cost only +7% and 0% at lab scale, because fixed per-statement overhead dominates tiny increments. At production volume this would be a large regression of the hourly job.

  • Recent-window CI data cannot see window changes

    Widening a 180-day window to 730 days (s01, truth +111%) read as −5% on a last-90-days sample.

  • History comparisons are fragile for tiny, frequent queries

    For s04, a 7 ms dashboard query's history median (10.9 ms) against one CI run (7.3 ms), times 30,000 runs a month, swamped a +673% per-run regression of the hourly model. A paired A/B run cancels drift like this; comparing against history does not.

E9Measured, dbt-core 1.12.5

Does change detection find the affected models?

Three detectors were compared on the 26 PRs: the changed files, dbt's state:modified, and a diff of the compiled SQL of every model.

  • 25 of 26 matched. dbt's state comparison agreed with the compiled-SQL diff at model level. It caught a macro edit fanning out to three models, a folder-level config change reaching five staging models, and in-file materialisation changes.
  • One miss. Changing a variable's default in dbt_project.yml (s24) made the hourly incremental model reprocess 15 times more days, and dbt reported nothing. The compiled-SQL diff caught it.
  • Changed is not the same as costlier. A cosmetic refactor with a renamed CTE (s21, truth −1%) and a macro edit touching three models (s23, truth +1%) were both flagged. Detection decides where to look; only measurement says whether it matters. A static screen settled 58 of 108 workload checks without running anything, mostly unchanged downstream models with identical plans.
  • Consumers live outside dbt. Dashboard queries were mapped from a registry that stands in for the platforms' access history. The workload-mapping table under E1 shows this step is required.
E5Computed from measured noise

Can confidence be grounded in numbers?

80% intervals were built by propagating measured run-to-run noise: the spread of a single CI run by duration, the noise in three history runs, and for the hybrid the disagreement between its two samples. A grade follows from the interval: high when it sits inside one class (increase, immaterial or decrease), medium when it spans two, low when it spans both directions.

Estimator80% interval covered the truthDirection right, by grade
Full-clone A/B with history84% (21 of 25)High 100% (19) · Medium 67% (6) · Low, none
Hybrid80% (20 of 25)High 94% (16) · Medium 71% (7) · Low 100% (2)
  • Coverage is close to nominal, and high-grade calls from the full clone were never wrong on direction.
  • The misses were near a threshold or dominated by millisecond queries (s12, s19), or right in direction with a systematic drift of 7–9 points that noise alone does not explain (s14, s22).
  • These intervals cover measurement noise only. A production interval also needs the CI-versus-production gaps (E3), physical layout (no effect in E8, but untested on real warehouse storage), frequency (E6), and pricing policy (E2). None of these could be quantified on a real platform.

The new-model scenario is excluded because its relative impact is infinite.

Does physical layout change the truth?

The same data was rewritten with row groups of 8,192 rows (about 1.7 days of line items) instead of the default 122,880 rows (about 26 days).

The hypothesis is rejected: layout granularity changed no ratio materially. Incremental-window changes look small in the lab because about 214,000 extra rows cost milliseconds against about 18 ms of fixed work per run. At 100 times the data, the same change would multiply the hourly job's scan work about 15 times. The lab therefore understates these regressions, and so would any CI run on less-than-production data.

E10Measured cost, assumed rates

Does the check pay for itself?

A check that consumes k production runs, triggered a few times per PR, is worth running only if it removes more expected cost than it spends:

k × runs per PR ≤ P(material regression) × typical regression × runs per month × months undetected

k was measured for each strategy. The break-even frequency was swept over a 5% or 20% regression rate, +50% or +100% typical regression, one or three months before discovery, and one or three CI runs per PR.

Strategyk (median)Break-even runs per month: min / median / max
Full-clone A/B4.67.7 / 69 / 552
PR-only run vs history2.54.1 / 37 / 299
10% key-consistent sample1.62.7 / 24 / 196
Hybrid4.06.7 / 60 / 480
Static plan00
  • The one strategy that met the accuracy bars pays off at median assumptions only on workloads run more than about 70 times a month, such as hourly jobs and dashboard queries. The PR-only run lowers that to just over daily.
  • A monthly job can never justify a clone run: one analysis costs about 4.6 of its monthly runs.
  • The hybrid does not save money (k of 4.0 against 4.6). Its static screen skipped unchanged descendants, but the sample stage then ran on the changed workloads, and most of them escalated to a clone anyway.
  • The most expensive analyses (k of 30–36) came from super-linear regressions and wide blast radii, so the check costs most when the PR is most dangerous. A per-PR spend cap with a "too expensive to measure" result is required.
  • Snowflake bills a 60-second minimum every time a CI warehouse resumes, which makes short sample runs cost more than their runtime (inferred).

  • Batch jobs on dedicated warehouses: marginal and attributed dollars agree. The 60-second minimum and idle time matter little for jobs that run for minutes, so cost per run times frequency is a fair estimate here.
  • Dashboard queries on a busy warehouse: the marginal cost is about zero and can have the opposite sign. The simulated dashboard warehouse is up all business day, so extra query time is absorbed until concurrency forces a second cluster. Whether to report short-run marginal spend or capacity consumed is a policy choice, not a measurement.
  • Billing models differ by orders of magnitude. The compute-heavy join costs +$208 on Snowflake and +$1 under BigQuery on-demand. The byte-heavy full rebuild costs +$282 on-demand and +$47 on Snowflake. How PRs rank by cost depends on the platform.
  • Capacity pricing adds rounding. BigQuery editions allocate slots in steps of 50 held for at least 60 seconds, so batch changes cost more than their slot-seconds suggest (s01: $62 against $34). The dashboard pool's 100 baseline slots absorbed dashboard changes entirely.
  • The pattern holds at other scales. On the dedicated Snowflake pool, from a scale factor of 10 to 1,000, dashboard changes stay absorbed (at 1,000: $0 marginal against +$167 attributed for s19) and batch changes stay close to attributed. Idle-time effects grow for the short hourly job (s03 at 1,000: +$8 marginal against +$45 attributed).
These dollars are not forecasts. They show mechanisms under documented billing rules applied to a synthetic month. The replay has not been checked against real metered bills; that is the first item of the live experiment. One defect in the simulator was found and fixed during this work: rounding residue created phantom autoscale charges.

Does a CI measurement hold under production conditions?

In E1 the full clone ran under the same conditions as the truth, which flatters it. Here six scenarios were re-measured under conditions where CI and production usually differ.   • CI must match the production warehouse size. A smaller engine overstated regressions by up to 136%, because MAIN and PR parallelise differently, and turned a production improvement (s22) into a regression. The error is not a constant factor, so one global correction cannot fix it. For Snowflake this implies (inferred) that an X-Small CI warehouse is no proxy for a Large production one: CI must run at the production size, or be calibrated per pool.
  • Concurrent load shifted ratios by −18% to +58% while keeping their direction. The load was two heavy aggregations running alongside, like other tenants of one warehouse; it slowed absolute runtimes 2.6–4.5×. This depends on what else runs, so it belongs in the interval, not the estimate.
  • Warm-up matters. A cold single run understated ratios by up to 29%.
  • E1's accuracy for the full clone is therefore an upper bound. A high-grade verdict needs CI compute of the production size and an interval widened for contention.

Hypothesis verdicts

HypothesisVerdictWhy
H1 Change attributionSupportedWith two fixes: a compiled-SQL diff next to dbt's state comparison, and consumer discovery from the platform's access history.
H2 Counterfactual estimationOnly by executionSupported only by production-scale execution. The full clone had 100% direction and no sign errors. Every cheaper estimator (static, bytes, four sampling schemes, extrapolation) made wrong-sign or missed-material errors.
